## 2. 原始內容、生成流程、提示詞與輸出格式

### 2.1 原始內容在哪裡

研究證據主要在原研究的 HANDOFF 與舊報告，工程驗證在協作交接；發布操作及功能文字在另一 repo 的 README／手冊。最新版成功回報只在對話中直接提供，再由模型整理入文件。不同材料的原始性並不相同：交接轉錄不是原匯出附件，後來整理的 evidence 也不是新增實驗。

### 2.2 實際生成方式

本次檢視的兩 repo 原始碼中，未找到「總結研究」應用功能、摘要 API 串接或專用生成器。既有總結是本對話中讀取文件後，由助理直接撰寫 Markdown，再以本機腳本寫檔、commit、push。後續收到補充要求後增寫 paper 與入口，沒有一個已存在、可直接重跑的研究生成管線。

可由對話及提交紀錄確認的提示演進是：先要求脫敏且只保留研究、不要 code、給結論；再補成功環境與未重開；接著追問假說、推導；最後要求按論文看待。現有 repo 未保存一份完整、可重用的「總結研究」生成規範。確切模型版本、採樣參數與所有生成執行記錄未在 repo 保存，不能虛構其設定。

### 2.3 輸出與呈現

第一個提交產生 6 份 Markdown；第二個提交新增 paper，形成 7 份 Markdown。沒有獨立摘要 UI、編輯器或網站。當時的呈現問題主要是 GitHub 文件入口、重複資訊和連結，而非已證實的前端渲染 bug。

原先要求以研究 repo 整理，這次才明確擴大成研究與發布 repo 都納入。不能把新增加的範圍倒算為早先未遵守指令；但現有總結確實尚不足以滿足目前跨 repo 的審查及總結需求。

## 4. 缺陷證據、原因與修正

以下根因判讀中，文件矛盾、檔案缺項與生成步驟屬已觀察事實；對整理策略為何導致缺陷的解釋屬根據產物及修訂歷程的推論，不代表已知模型內部原因。

### Q01：證據鏈不足

**例子：** [sources 第 7 行](https://github.com/Platyun/ios-location-research/blob/8c3651f6c719876d15dfb9274e5840f6a57a48fd/docs/sources.md#L7)只給來源 SHA 與泛稱文件；[paper 的 E1](https://github.com/Platyun/ios-location-research/blob/8c3651f6c719876d15dfb9274e5840f6a57a48fd/docs/paper.md#L169)連到同批生成的 evidence，而非逐筆原材料。E-02 的新回報沒有可識別的脫敏直接摘錄與穩定紀錄 ID。

**原因：** 先寫敘事，再補來源頁；把整理稿當成來源終點。**修正：** 建立證據表，每筆記錄 ID、類型、收到日期、版本、來源定位、忠實摘錄、已知／未知與支持的主張。原附件不存在就明寫只有交接轉錄。**驗收：** 所有核心結論可追到明確記錄；生成稿不得單靠互相引用形成證據循環。

### Q02：方法描述不具重現性

**例子：** [paper 2.3](https://github.com/Platyun/ios-location-research/blob/8c3651f6c719876d15dfb9274e5840f6a57a48fd/docs/paper.md#L41)只交代候選方法與缺新版紀錄，未整理實際測試 App 版本／build、安裝路徑、App 或 widget、配件、定位開關順序等。讀者不知道哪套產物對應哪筆結果。

**原因：** 「不帶 code」被處理成只剩抽象方法描述；研究協定與原始碼沒有區分。**修正：** 用純文字協定表呈現已知流程與未知欄，分開預定流程、發布手冊流程及使用者確認的實際流程。**驗收：** 每筆結果均有介入及產物對應欄；未知不得由發布版設計補成已執行。無須為補文件要求重測。

### Q03：終點與前置條件沒有分層

**例子：** [conclusion 第 7 行](https://github.com/Platyun/ios-location-research/blob/8c3651f6c719876d15dfb9274e5840f6a57a48fd/docs/conclusion.md#L7)以「失效後」為問題，直接接最新成功即目標達成；但 [evidence 第 19 行](https://github.com/Platyun/ios-location-research/blob/8c3651f6c719876d15dfb9274e5840f6a57a48fd/docs/evidence.md#L19)明列舊測試按前是否失效未記錄，最新回報也沒逐項記錄此狀態。

**原因：** 接受成功回報後，敘事把研究背景中的前置條件一併帶入結果。**修正：** 分列「使用者回報未重開可套用」「已記錄失效後恢復」「介入因果」「機制確認」。目前第一層有明確回報，其餘按材料判斷。**驗收：** 每個結果句均標明證據層級；不否定使用者回報，也不默認未知的失效基線。

### Q04：發布成果沒有進入總結

**例子：** [paper 的資料範圍](https://github.com/Platyun/ios-location-research/blob/8c3651f6c719876d15dfb9274e5840f6a57a48fd/docs/paper.md#L33)未納入發布 repo；全文沒有把手動後端、gate、兩個送出路徑、兩種 IPA 和各自驗證狀態組成矩陣。

**原因：** 原生成來源以研究為主，後續只增加論文形式，沒有在目前範圍擴大時重建來源清單。**修正：** 新增跨 repo 的「功能 → 實作 → 檢查 → 真機結果 → 未知」矩陣。**驗收：** 研究與發布兩個固定版本均列入；建置、假後端測試、封裝、安裝、真機效果不混算。

### Q05：研究說明自相矛盾

**例子：** [研究 App README 第 23 行](https://github.com/Platyun/itool-fix/blob/5ede53336972543a4c79cb5540029ed837b82146/Platyun-Location-Service-Probe/README.md#L23)說強制結束會重置冷卻，[第 69 行](https://github.com/Platyun/itool-fix/blob/5ede53336972543a4c79cb5540029ed837b82146/Platyun-Location-Service-Probe/README.md#L69)卻說不會。同頁第 7 行有介面存在及返回紀錄，第 11 行仍說尚未確認保留此介面。

**原因：** 加入跨程序版本時追加新段落，沒有將舊說明標成歷史；總結未做來源衝突清單。**修正：** 現行、舊版及 fallback 分節，現行行為對照 gate 與 App Groups 設定；舊真機結果不改寫。**驗收：** 同一版本／模式不得同時出現相反描述，總結採信順序要明示。

### Q06：設計被寫成已驗證的發布能力

**例子：** [發布 README 第 23 行](https://github.com/Platyun/reset.loacation.by.Platyun/blob/5790b4f0d18257b6f293ab005b12d94c62efec08/README.md#L23)直接說小工具背景送出且不開 App；[研究驗證第 21 行](https://github.com/Platyun/itool-fix/blob/5ede53336972543a4c79cb5540029ed837b82146/handoff/codex-to-claude.md#L21)仍把是否不開 App、介面及效果列為待真機確認。

**原因：** 功能介紹依程式意圖撰寫，未附對應驗證狀態。**修正：** 就近標為「已實作，真機待確認」，直到有特定環境與路徑的證據。**驗收：** App 的成功不能自動勾選 widget；靜態程式判讀與裝置結果分欄。

### Q07：組合流程被提升為必要條件

**例子：** [發布手冊第 43–50 行](https://github.com/Platyun/reset.loacation.by.Platyun/blob/5790b4f0d18257b6f293ab005b12d94c62efec08/docs/manual/操作手冊.md#L43)標「每次操作必要流程」，包含特定配置及兩個藍牙。但研究未獨立隔離配置效果，也未證明每種環境都需要兩個藍牙。

**原因：** 個人既有操作被改寫為普遍操作協定，適用範圍遺失。**修正：** 明列此為已記錄的特定設定流程，區分必要條件與尚未驗證的組合條件；不要自行刪除使用者原流程。**驗收：** 每個「必要／必須」都能追到產品限制、明確適用條件或比較證據；否則降為條件性說明。

### Q08：環境資訊未跨 repo 同步

**例子：** [發布 README 第 8 行](https://github.com/Platyun/reset.loacation.by.Platyun/blob/5790b4f0d18257b6f293ab005b12d94c62efec08/README.md#L8)仍只有 iOS 27.0.1，而純研究稿已列 iOS 27.2.1。

**原因：** 新回報只加入新文件，沒有環境／驗證狀態的共同索引。**修正：** 留下舊結果並新增帶日期與安裝路徑狀態的新列，不單純覆蓋系統數字。**驗收：** 各入口能找到最新回報，且不把它默認綁定到未確認的下載包。

### Q09：假說過廣且缺少反駁條件

**例子：** [paper H1](https://github.com/Platyun/ios-location-research/blob/8c3651f6c719876d15dfb9274e5840f6a57a48fd/docs/paper.md#L125)是「某種可變狀態參與失效」，涵蓋面廣，幾乎任何恢復都相容；H2 的前後順序測試仍受等待及順序效應影響。

**原因：** 為避免過度斷言而退到難以反駁的概念，再以論文語氣包裝。**修正：** 分開研究方向與可測假說；每個可測假說列出可觀察預測、反對證據、競爭解釋與不能區分的結果。順序測試只能增加線索，不宣稱已排除時間效應。**驗收：** 每個列為「可測」的假說都有至少一項會降低其支持度的具體結果；無法列出的只標研究方向。

### Q10：資訊層級與語句冗餘

**例子：** README、conclusion、evidence、research 及 paper 多次覆述兩筆成功和同一組機制限制；paper 的摘要、結果、4.5、5.1、限制、結論又重複這些資訊。「實際暴露」「反事實」「療效」增加閱讀成本，沒有補充介入細節。

**原因：** 追問時追加新文件與段落，沒有指定唯一主文與各層文件職責。「當論文」被轉成擴章，而不是提高可查證資訊密度。**修正：** 主文集中資料、方法與推導；README 只保留摘要及入口；結論不再長篇覆寫證據表。改用「實際做了哪個操作」「未操作時的結果」，不借用不適合此題的臨床用詞。**驗收：** 除摘要及結論外，事件詳情只維護一份；其餘以連結引用。

### Q11：背景引用未落到具體命題

**例子：** [來源表](https://github.com/Platyun/ios-location-research/blob/8c3651f6c719876d15dfb9274e5840f6a57a48fd/docs/sources.md#L13)列 9 個來源，但 paper 主要只用 header 與 wloc 泛頁。僅能看到來源用途概述，無法逐條分辨哪些具體外部命題已核實、哪些只是原研究轉述。

**原因：** 把保留書目當成主張引用；沒有引用版本、節次與查驗結果的對應欄。**修正：** 區分直接使用、歷史背景及未核實候選來源，對正文每個外部命題給出適用版本與段落。**驗收：** 非使用者資料的技術主張都有直接支持來源；不能讀到正文者標未核實，不用來強化結論。

### Q12：ZIP 閱讀路徑損壞

**例子：** 本次直接讀取發布的 Platyun-Location-Download.zip，README 連到 download 下的兩份 IPA、側載安裝說明、SHA256SUMS，但這四個目標不在 ZIP 內；README 也不是目前 repo README。

**原因：** 直接把 repo README 複製進不同目錄結構的下載包，沒有依交付載體重寫連結。**修正：** 為 repo 與離線包使用各自有效的連結，或明確指向線上固定版本。**驗收：** 解壓後逐一檢查內部相對連結，失效數必須為零；不得只測原始 repo 的連結。

### Q13：UI 狀態被合併描述

**例子：** [手冊第 104 行](https://github.com/Platyun/reset.loacation.by.Platyun/blob/5790b4f0d18257b6f293ab005b12d94c62efec08/docs/manual/操作手冊.md#L104)說「處理中或冷卻中」顯示倒數；[widget 第 107–114 行](https://github.com/Platyun/reset.loacation.by.Platyun/blob/5790b4f0d18257b6f293ab005b12d94c62efec08/PlatyunLocationWidget/PlatyunLocationWidget.swift#L107)則分別為正在送出文字與冷卻倒數。

**原因：** 文件沒有逐項對照狀態分支。**修正：** 將處理中、冷卻、逾時提示、可送出、無群組分列，註明真機畫面更新尚未驗證。**驗收：** 文件狀態表與來源分支一對一；不能由此靜態差異推定實機渲染壞掉。

### Q14：生成驗收層次錯置

**例子：** 先前可見檢查是 Markdown-only、個資字串、署名、相對連結及 git diff；這些通過後，Q01–Q11 的語意問題仍存在。下載包的 Q12 也未被原文件連結檢查攔下。

**原因：** 沒有「證據整理 → 主張矩陣 → 草稿 → 跨來源衝突審查 → 各載體檢查」的分階段流程；缺少可重用規範及回歸案例。無法據此認定是特定模型版本或採樣參數造成，相關設定並未保存。

**修正：** 用下節生成規範及驗收矩陣作門檻。**驗收：** 機械檢查與語意審查都要完成；不得以篇幅、章節數、通過建置或模型自評取代內容驗收。

## 5. 四類問題如何區分

| 類別 | 已確認的問題 | 不應混淆的事項 |
| --- | --- | --- |
| 內容品質 | 證據定位不足、方法缺欄、主張層級不清、版本矛盾、發布能力混寫。 | 缺少新真機資料是研究限制，不自動等於文字捏造。 |
| 提示詞／規格設計 | 沒有固定來源範圍、必填資料表、可引用主張清單、缺資料處置及驗收規則。 | 使用者原要求簡短，不免除生成端核對資料的責任；新範圍亦不倒算舊錯。 |
| 模型輸出／整理行為 | 以論文外觀擴寫、抽象化介入、重複限制、把背景前提帶入結果。 | 不能在沒有模型紀錄時推定某模型本質較差或調參即可解決。 |

## 6. 根因與改善優先順序

**根因鏈：** 未先建立來源及版本表 → 沒有事件／主張對應 → 從對話直接寫多份敘事 → 用論文章節補充形式 → 缺少跨 repo 與發布載體檢查 → 文件逐次追加而失配。這些可由現有檔案、提交及對話觀察支持；不推定不存在的後端摘要服務。

| 順序 | 具體工作 | 交付及完成條件 |
| --- | --- | --- |
| 先修 | Q01–Q03、Q05：建證據表、分層主張、補方法未知欄、整理現行／歷史矛盾。 | 核心結論逐句有來源；不知道的保留未知；矛盾為零。 |
| 接著 | Q04、Q06、Q07、Q08：跨 repo 能力矩陣、發布適用條件與環境同步。 | 每項功能標已實作／既有測試／本次檢查／真機回報／未知。 |

## 7. 建議內容架構與生成規範

### 7.1 唯一主文架構

1. 一段結論：確定收到的回報、適用範圍、尚不能推論的機制。
2. 來源及版本：兩 repo 固定 SHA、直接回報、原始與轉錄的區別。
3. 研究問題與終點：成功、失效基線、因果及機制分層。
4. 事件與介入表：每筆的環境、產物、操作、輸出、觀察及未知。
5. 發布能力／驗證矩陣：實作與各層驗證分開。
6. 假說推導：前提、觀察、競爭解釋、預測與反駁條件。
7. 討論與限制：只列會改變結論範圍的限制，不反覆泛稱未驗證。
8. 結論、待辦、引用：區分已完成與建議工作。

README 只放摘要及 HTML／Markdown 入口；證據詳細表只維護一份。論文形式是表達選項，不能替代上述證據結構。

### 7.2 可重用生成規範

**任務：** 根據指定研究 repo、發布 repo 及直接補充，生成可追溯、脫敏的研究及產品狀態總結。先抽取資料，再寫敘事。

**輸入契約：** 固定版本、來源清單、逐筆證據、直接摘錄、來源可信範圍、目前實作、既有驗證及本次實際執行的檢查。不同版本的結果不得合併為同一次試驗。

**處理順序：** 列出所有核心主張 → 對應支持及反對材料 → 找衝突並依日期／版本判讀 → 標未知 → 產生能力矩陣 → 寫主文 → 反查每個結果句 → 檢查各交付載體。

**禁止事項：** 不補編操作、結果、模型參數或成功率；不由程式存在推定真機成功；不由 YES 推定重啟或清快取；不把背景中的失效狀態當成每次測試已確認；不把新版本自述套到所有下載包；不以持續時間增加使用者未要求的驗收門檻。

**輸出契約：** Markdown 為內容原稿，HTML 從同稿產生；兩者包含相同的主張、來源、限制及修正狀態。允許只輸出文件，不要求帶入 code 或密件。缺資料時標未知，不為填滿欄位要求無關重測。

## 8. 可客觀驗證的品質標準

| 門檻 | 通過條件 | 如何驗證 |
| --- | --- | --- |
| 核心主張追溯 | 100% 結果及因果主張有證據 ID、類型與穩定來源；直接對話有脫敏摘錄定位。 | 人工逐句對照主張矩陣，不只檢查網址存在。 |
| 不擴張證據 | 0 個把已實作、測試、建置、安裝、真機效果互相替代的句子。 | 跨來源語意審查及反例測試。 |
| 前置狀態 | 每筆明列失效基線為已確認／未記錄；未記錄不改寫為確認。 | 檢查事件必填欄與摘要措辭。 |
| 方法完整 | 每筆均列裝置、系統、App／build、送出路徑、實際操作、原始輸出、結果、安裝方式；未知可填未知。 | 欄位齊備檢查及來源抽查；有欄不等於資料已取得。 |
| 版本一致 | 同版本／模式的互斥行為敘述為 0；歷史行為清楚標日期。 | 研究、發布及總結交叉比較。 |
| 可測假說 | 每項都有預測、反對條件及競爭解釋；否則降為研究方向。 | 論證審查，不用章節數替代。 |
| 引用有效 | 正文技術主張均有直接來源及查驗狀態；未讀內容不作已核實依據。 | 檢查來源段落是否支持主張。 |
| 不重複維護 | 詳細事件只在一處維護，其餘連結；摘要可重述短結論。 | 比較事件段落及更新清單。 |
| 連結與封裝 | repo 及離線 ZIP 內相對連結失效均為 0。 | 對兩種目錄結構分別解析檢查。 |
| HTML／Markdown 一致 | 標題、缺陷 ID、嚴重程度、結論及來源一致；無外部腳本或個資。 | 從同一 Markdown 轉換，解析 HTML 比對文字及連結。 |

| 完成宣告 | 修正建議、已修項、未測項清楚分開。 | 審查 diff 與實際命令／結果，不接受只有模型自評。 |

### 防止重犯的回歸案例

- 只有「YES」而無位置回報：只能寫方法返回，不得寫定位成功。
- 只有「成功、沒重開」而無安裝方式：保留成功回報，安裝路徑填未知，不勾選側載驗證。
- 只有假後端 40 PASS：不得勾選 widget 真機成功。
- 新舊文件冷卻行為相反：必須列衝突，不得自選一句當現行而不查版本。
- 使用者說持續時間不是重點：不把它設為操作成敗門檻。
- ZIP 未包含 IPA：不得生成指向包內 IPA 的相對下載連結。

## 9. 應保留的內容

明確分開 YES 與清快取、保留使用者未重開成功回報、把不同版本分列、不計算缺少分母的成功率、對 SDK 與裝置系統作區別，以及標出示意圖而非真機截圖，這些做法合理，不因整體品質不佳而刪掉。

本次沒有證據顯示所有內容都錯，也沒有證據支持將問題歸因於獨立「總結研究」UI。核心問題是整理與驗收方法不足，修正方向應先改善證據和版本結構，再整理文字與排版。
