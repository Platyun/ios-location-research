2. 研究實際回答了什麼

研究問題從約 20 km／回跳現象，收斂到「既有定位流程失效後，能否免整機重開重新套用」。早期調整網路條件沒有改善，後來配置加重開曾恢復，因此形成可變定位狀態的調查方向。舊 runtime header 提供候選入口；首次真機紀錄再確認該次方法存在且能返回。

這段脈絡解釋為什麼值得測試候選入口，不構成基地台快取根因的證明。完整推導須保留競爭解釋：控制 App／配件重連、等待、定位開關、配置及未記錄操作都可能參與。

3. 發布版到底做了什麼

候選入口後端會先檢查方法與回傳簽章，送出前再次驗證，再透過 runtime 呼叫候選方法。輸出記錄正常返回、零／非零或例外，沒有讀取座標來自動判定定位成功。

主 App 有明確送出確認及紀錄。小工具有獨立送出路徑，與 App 共用 gate；處理中拒絕重入、返回後冷卻 10 秒。沒有 App Groups 的配置另有 fallback。這些是來源程式所實作的行為，相關真機表現仍須按路徑分別記錄。

4. 如何理解發布操作流程

發布手冊保存的流程為 VPN、配件連接、關閉定位、手動請求、開啟定位，最後回原工具確認。這是目前產品文件所寫的組合流程，不是本次回報逐步確認過的協定，也沒有證明每一個條件都是必要條件。

因此，不能把「兩個藍牙」「特定配置」「固定順序」一概寫成所有裝置必須具備的科學結論。使用者既有設定可保留為操作背景；若要驗證必要性，須有相應變因比較。

5. 已知差異與交付風險

  • 研究 App README 同時存在強制結束會／不會重置冷卻的相反敘述，反映不同版本被混寫。
  • 發布文件仍以 iOS 27.0.1 為測試環境，新回報尚未同步；不能把新回報默認套到所有下載包。

這些是文件與發布流程缺陷，不表示核心呼叫程式已被證明失效。逐項證據、根因與修正順序見 完整品質審查。
