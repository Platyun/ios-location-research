3. 新增缺陷

Q15：研究起點 itool-fix 沒有寫進總結

例子： 前一版總結只說「研究問題從約 20 km／回跳現象」開始，沒有日期、沒有連結，也沒說明起點是 itool-fix 的早期研究：iTools BT 2.5、iOS 18 與 iOS 27 兩台設備對照、Shadowrocket 五種條件測試。itool-fix 在來源表裡只被當成「原研究 repo」，用途寫成交接與工程紀錄。

為什麼是問題： 讀者看不出研究為什麼從距離限制轉到重開整機，也看不出早期對照實驗已經排除了哪些方向。舊稿把配件泛稱化，也讓早期結論無法回查。

原因： 脫敏時把「不限定單一配件」理解成「不寫起點配件」，再以研究交接為主要來源，略過了更早的研究文件。

已修： 主文第 2 節新增起點與問題演變時間線，附行號連結。

Q16：27.0.1 → 27.2.1 的先後關係被誤述

例子： 前一版與舊稿把兩筆寫成「先前紀錄」與「最新補充」，強調「不同版本不能當成同條件重複試驗」，舊研究稿 2.3 還寫新回報的「確切介入暴露未獨立確認」。但使用者的實際情況是：同一台手機在 27.0.1 實測通過，之後更新到 27.2.1 再複測成功（U-06）。

為什麼是問題： 這是研究最重要的結果之一：做法在系統更新後仍然有效。原寫法只防止了「兩筆當成獨立樣本」的錯誤，卻把「更新後複測」這個實際發生的事拆散，讀者讀不出兩筆的關係。「複測」也已說明使用者重複了同一測試，不是在研究脈絡外發生的偶然成功。

原因： 把「不能推定」用到過頭：因為缺少新版返回值，就連使用者說明過的測試關係也不寫。生成時沒有把使用者的原話當作時間線資料保存。

已修： 結論第一句、時間線、事件表與結果分層都改為更新後複測；新版返回值、安裝產物、送出路徑仍標未知。

已修： 本次實際重跑 SHA-256、IPA 比對與 ZIP 連結檢查，E-04 只寫本次結果。「6 個核心檔相同」本次沒有重跑，已從主文移除。

4. 四類問題的區分

類別這次確認的問題不應混淆
內容品質起點遺漏（Q15）、更新後複測被拆散（Q16）、證據鏈與方法欄位不足（Q01、Q02）、結果未分層（Q03）。缺少新的真機資料是研究限制，不是文字捏造。
提示詞與規格沒有要求保存使用者原話與時間順序、沒有指定研究起點、沒有規定唯一主文。使用者早先要求簡短，不免除整理者核對來源的責任。
模型輸出為了避免過度斷言而退到抽象泛稱（Q09、Q16）；同一組限制反覆覆述（Q10）。沒有模型紀錄，不能推定特定模型或參數是原因。
UI 呈現HTML 窄螢幕表格、焦點樣式（Q18）；發布文件的狀態標示（Q06、Q13）；ZIP 連結（Q12）。這個 repo 沒有「總結研究」App 介面；問題都在文件與 HTML。

5. 生成規範

輸入： 兩 repo 的固定 SHA、研究起點文件、使用者原話（附收到日期與 ID）、本次實際執行的檢查。

順序： 先建時間線與事件表 → 列出每個主張與支持它的紀錄 → 找衝突並標明適用版本或模式 → 標未知 → 寫主文 → 逐句反查 → 檢查兩種格式與連結。

必須做到：

  • 結論第一句寫出使用者實際做了什麼、在哪個裝置與版本、結果如何。
  • 研究起點、問題轉向與每次測試按時間排列，附原始文件行號連結。
  • 使用者原話保留為直接摘錄，不改寫成較弱的說法。
  • 同一裝置的先後測試寫成先後測試；不能把它們當成獨立樣本，但也不能拆成互不相關的兩筆。
  • 每個可測假說寫出「若成立應看到」與「看到什麼會削弱它」；寫不出的標研究方向。

禁止： 補編返回值、失效狀態、安裝方式、試驗次數或成功率；用程式存在推定真機成功；用 YES 推定重啟或清快取；把持續時間設為門檻；把前次檢查寫成本次重跑。

回歸案例

  • 使用者說「A 版本通過後更新成 B 版本複測成功」：要寫成同一裝置的先後測試，不能拆成兩筆無關回報。
  • 研究起點在另一個 repo：總結要有起點日期與連結。
  • 只有 YES，沒有位置結果：只能寫方法返回，不能寫定位成功。
  • 只有「成功、沒重開」，沒有安裝方式：保留成功，安裝方式標未知，不勾側載驗證。
  • 只有假後端 40 PASS：不能勾小工具真機成功。
  • 兩段文件說法相反：先查是不是不同模式或版本，再決定怎麼標示，不能直接判定其中一句錯。
  • 使用者說持續時間不是重點：不設為門檻。
